# Phase 4 商品特定 設計書

承認済み(2026-10-18)。要件: `docs/product-identification-requirements.md`。API の調査: `docs/phase4-api-research.md`。Phase 3 の設計: `docs/superpowers/specs/2026-10-15-phase3-detection-design.md`。

## 1. 範囲

**作るもの**
- `POST /v1/identify`(アイテム 1 件ぶんの商品特定)
- 検索語の生成、SerpApi(Google Shopping)と楽天市場商品検索 API の検索、候補の照合と A・B・C の判定
- 検索結果のメモリキャッシュ、使用量の記録と上限、月間予算の警告と停止
- モバイルの「商品を探す」ボタン、候補の表示、楽天のクレジット表示
- 実 API での評価スクリプトと、評価結果の記録

**作らないもの**: Google Lens(画像検索)、本物の認証、有料プランの管理、商品のデータベース、ほかの EC。Lens は、案 A の精度を測ったうえで、必要なら別 Phase で検討する。

**実行のタイミング**: アイテムごとに、ユーザーが「商品を探す」を押したときだけ。`POST /v1/analyze` は変えない。

## 2. 流れ

`POST /v1/identify`

- 入力(multipart):
  - `image`: 切り抜き画像(JPEG/PNG)。Phase 3 と同じ検証(マジックバイト、画素数、サイズ)を通す。
  - `item`: Phase 3 の検出結果の JSON(カテゴリ、色、柄、読み取れた文字、ブランド候補)。zod で検証する。
  - `X-Install-Id` ヘッダー: アプリが作る匿名のインストール ID。
- 出力: 判定(A・B・C)、候補の一覧、候補ごとの「一致した点」「確認できていない点」、使った検索の種類、使えなかった検索、使用量(トークン数・検索回数)。

処理順(1 アイテム):
1. **検索語の生成**: Claude が検索語を 1〜3 個作る。ブランドは、読み取れた文字がある場合だけ使う。
2. **検索**: SerpApi と楽天を並行して実行する(各 1〜2 回まで。追加検索は、必要なときだけ 1 回)。
3. **候補の整理**: 重複を除き、取得できた項目だけを `Product` に詰める。取れない項目は空にする。
4. **照合**: Claude が、切り抜き画像と候補(商品名・サムネイル)を比べる。
5. **判定**: 3 章のルールで A・B・C を決める。

検索が片方だけ失敗・未設定のときは、もう一方で続け、使えなかった検索を結果に明示する。両方使えなければエラーを返す。ダミーの結果は返さない。

## 3. 判定のルール

**A(特定)**: 次を全部満たすときだけ。
1. 写真から読み取れた文字に、ブランドが語として現れる(Phase 3 と同じ基準)。
2. 候補の商品名か型番が、読み取れた文字、またはカテゴリ・色・形の特徴と合う。
3. 候補のブランドが、1 のブランドと一致する。
4. 切り抜きと候補の画像を Claude が見比べて、同じ商品と判断する。外観が似ているだけなら不可。

どれか 1 つでも欠けたら B にする。商品ページが存在することだけでは A にしない。

**B(候補あり)**: 最大 5 件。各候補に「一致した点」「確認できていない点」を文章で付ける。`matchType` は `similar`(同一とは言わない)。

**C(特定できず)**: 手がかりが無い、または合う候補が無い。「特定できませんでした」と表示し、商品名やブランドを作らない。楽天に無い商品を、楽天にあるように見せない。

**確信度**: Claude が出す数値は、一致の目安としてだけ使う。実測された正解確率として表示しない。画面には、A・B・C と、一致した点・未確認の点を出す。

**価格**: 種別は、販売価格(楽天)、表示価格(Google Shopping)、不明。定価・セール前の価格は、取得できたときだけ区別する。取れなければ空にする。出典と取得日時を付け、画面にも「○月○日時点」と出す。

既存の `DetectedItem` の `candidates`、`level`、`confidence`、`rationale` に結果を入れる。`level` は A→`high`、B→`low`(Phase 3 でブランド採用済みなら `medium`)、C→`unidentified`。

## 4. 費用・上限・保存

- **検索回数**: 1 アイテムで SerpApi 1〜2 回、楽天 1〜2 回まで。失敗した検索は再試行しない。1 回の検索のタイムアウトは 15 秒以内。
- **キャッシュ**: 同じ検索語・条件の結果をサーバーのメモリに保存する(既定 1 時間、設定値)。ファイルやデータベースには保存しない。楽天の規約(不特定多数が共有できる保存の禁止)の範囲に収める。
- **使用量の記録**: Claude のトークン数、SerpApi の検索回数、楽天の呼び出し回数、1 アイテムあたりの推定原価。保存先は小さなローカル SQLite ファイル 1 つ。数値の集計だけで、写真・画像・検索結果は入れない。
- **月間予算**: SerpApi の月間検索数が設定した上限の 80% でログに警告。上限に達したら SerpApi を止め、楽天だけで続ける(画面に表示する)。
- **利用者ごとの上限**: 匿名のインストール ID と IP で、1 日あたりの回数を制限する。これは認証ではない。有料プランの前に、本物の認証が必要。
- **料金**: 設定値で持ち、ソースに固定しない。

## 5. セキュリティと未設定時の動作

- キーはサーバーの `.env` のみ(`SERPAPI_API_KEY`、`RAKUTEN_APPLICATION_ID`、`RAKUTEN_ACCESS_KEY`、`RAKUTEN_AFFILIATE_ID`)。ログには、キー・画像・検索語の全文を出さない(種類と回数だけ)。
- 楽天の `accessKey` はクエリパラメータで渡す(実測で確認済み。`Authorization: Bearer` は 400 だった)。
- 外部の URL(候補のサムネイル)を取得する場合は、https のみ、許可ドメインのみ、サイズと時間の上限つき、リダイレクト無しとする。Claude に URL は渡さない(Google のサムネイルは Anthropic 側の取得が robots.txt で拒否されるため)。サーバーが取得し、base64 で渡す。画像は SerpApi の `serpapi_thumbnail`(serpapi.com/images/url/)と楽天のサムネイルに限る。
- キーが未設定の検索は使わず、結果に「未設定」と返す。アプリ全体は落とさない。
- 楽天のアフィリエイト ID が未設定なら、アフィリエイトなしのリンクを使い、収益化されないことを記録する。

## 6. モバイル

- 結果画面の各アイテムに「商品を探す」ボタン。押したアイテムだけを送る。切り抜き画像は、Phase 3 の枠からクライアントで作る。
- 検索中は、そのアイテムのカード内に進行表示。
- 候補はカード内に最大 5 件表示。商品名、ブランド、価格(種別・取得日時つき)、購入先のリンク、一致した点と未確認の点。
- 楽天の候補が出る画面には、「Supported by Rakuten Developers」を表示する。
- 未設定・上限到達・失敗は、日本語で理由を表示する。

## 7. テスト

- 判定ルール(A になる条件、B に落ちる条件)は固定の入力で検証する。
- SerpApi と楽天のクライアントは、HTTP の境界を差し替えて、応答の形、エラー、未設定、429、タイムアウトを検証する。
- 上限、キャッシュ、予算停止の動作を検証する。
- モバイルは、ボタン、進行表示、A・B・C の表示、未設定の表示を検証する。
- 実 API を使う確認は、自動テストに入れず、評価スクリプトに分ける。

## 8. 評価

- 評価スクリプトが、手持ちの写真 10 枚を解析し、アイテムごとに商品を探して、A・B・C の件数、候補、1 アイテムあたりの原価を表にする。
- SerpApi の無料枠(月 250 回)を守るため、1 回の評価の検索は 40 回以内にする。
- 候補が正しいかは、目視で写真と照らして確認し、`docs/` に記録する。

## 9. 確認が残る点

- SerpApi のデータの商用利用・保存の条件(SerpApi への問い合わせが必要)。
- 楽天の想定 QPS の上限と、料金が発生する条件。
- 〔確認済み〕Shopping 結果のサムネイルの形式: `thumbnail`(gstatic)は Claude に URL で渡せない。`serpapi_thumbnail`(WebP)をサーバーが取得して base64 で渡す。
- 文字が読めない服は、ほとんど B か C になる見込み。精度を測ってから、基準を調整する。
