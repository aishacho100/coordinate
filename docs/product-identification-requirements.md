# 商品特定 API 構成の要件(ユーザー指示書)

ユーザーが 2026-10-15 に提示した要件。Phase 4 以降の設計・実装の基準とする。Phase 3 では検出までを対象とし、このうち Claude API 部分とトークン記録だけを取り込む(範囲は `docs/superpowers/specs/2026-10-15-phase3-detection-design.md` を参照)。

## 1. 目的

ユーザーがアップロードしたコーデ写真から服・靴・バッグ・アクセサリーなどを特定し、ブランド名、商品名、価格、購入先 URL を提示する。将来的な有料プランとアフィリエイト収益で利益を出すことを目指すため、商品特定の精度・API 利用料・運用費・拡張性・セキュリティを重視する。既存の実装を壊さずに進める。

## 2. 使用する API

### 必須①: Anthropic Claude API

用途: 画像の内容分析、カテゴリ判定、色・形・柄・素材感・ロゴ・ディテールの抽出、検索キーワードの生成、検索結果の商品候補と画像の特徴の比較、判定結果の出力。

- 利用可能な画像対応モデルを公式ドキュメントで確認する。
- モデル名はソースに散在させず、環境変数などで管理する。
- 画像から直接観察できた事実と、推測した情報を区別する。
- Claude の回答だけで実在商品と断定しない。商品ページ・型番・画像などの根拠と照合してから判定する。
- JSON Schema 等で出力形式を検証し、不正な出力や API エラーを処理する。

### 必須②: SerpApi

用途: 商品名・ブランド名・特徴での Web 検索、画像検索、公式サイトや EC の商品ページの発見、Claude が生成した検索語での追加検索。

- 現在提供されている検索エンジン・検索タイプを公式ドキュメントで確認し、実際に使える機能だけを使う。
- 検索パラメータ、料金、利用制限を確認する。
- Google Lens の結果取得は、現在の対応状況を確認できた場合のみ。確認できなければ実装しない。
- Google 公式 API と SerpApi を混同しない。
- 検索結果を正解扱いしない。商品ページ URL・タイトル・価格・画像 URL・出典を保存する。
- 検索回数に上限を設け、結果をキャッシュして重複検索を減らす。
- 利用規約と取得データの再利用条件を確認する。

### 導入候補③: 楽天市場商品検索 API

用途: 商品候補の検索と補完、商品名・価格・販売ページ URL の取得、アフィリエイト収益につながる購入先の提示。

- 公式ドキュメント、利用条件、最新の提供状況、アプリ登録・認証情報・アフィリエイト設定を確認する。
- 実際に取得できる項目だけを使い、アフィリエイトリンクの利用条件を守る。
- 条件を満たせない場合は、未設定状態で安全に動作させる。
- 楽天で見つからない商品を、楽天に存在すると偽って表示しない。
- 検索対象を楽天市場の商品だけに限定しない。

## 3. Google Cloud Vision API

初期実装では必須にしない。まず Claude API と SerpApi の組み合わせで実装し、実際の写真で精度を測定する。OCR やロゴ検出が必要で、追加費用に見合う改善が見込める場合に限り導入を提案する。導入前に、Claude API との機能重複・追加費用・精度向上の見込みを比較する。

## 4. 商品特定の処理フロー

1. 画像の形式・サイズ・画素数を検証する。
2. 服・靴・バッグ・アクセサリーなどを識別する。
3. 各アイテムの特徴を Claude API で抽出する。
4. 特徴に基づいて SerpApi で商品検索を実行する。
5. 必要に応じて楽天市場商品検索 API でも候補を取得する。
6. 候補と元画像を、ブランド・商品名・型番・色・形・柄・ロゴ・画像の類似性などから比較する。
7. 情報が不足している場合だけ追加検索を行う。
8. 根拠を検証し、最終判定を行う。
9. 商品名・ブランド・価格・購入先 URL・確信度・出典・確認日時を返す。

複数のアイテムがある場合は、アイテムごとに独立して判定する。

## 5. 判定結果のルール

- **A. 高い確度で特定できた**: 商品ページ・型番・画像などの根拠が十分に一致している場合のみ表示する。
- **B. 候補は見つかったが確定できない**: 候補を複数表示し、何が一致し何が確認できていないかを説明する。
- **C. 特定できない**: 無理に商品名やブランドを作らず、特定できなかったことを明示する。

注意:

- AI が生成した確信度の数値を、実測された正解確率として表示しない。
- 根拠が弱い場合は確定判定を禁止する。
- 類似商品と同一商品を区別する。商品ページが存在することだけを理由に同一と判断しない。
- 不明な価格を推測で埋めない。定価・通常販売価格・セール価格を区別する。
- 価格を取得できた場合は出典と取得日時を記録する。

## 6. API 費用の管理

- Claude API の入出力トークン数、SerpApi の検索回数、楽天 API の呼び出し回数を記録する。
- 商品 1 件あたりの推定 API 原価を計算する。ユーザーごとの利用回数と費用を集計できるようにする。
- 検索回数・再試行回数・タイムアウトを制限する。同じ商品の重複検索をキャッシュで削減する。エラー時に無限再試行しない。
- 無料プランと有料プランの利用上限をサーバー側で管理する。
- 月間予算の警告と利用停止の仕組みを用意する。
- 料金はソースに固定せず設定値として管理する。公式料金を確認できない場合は、推測値を確定情報として記載しない。

## 7. セキュリティ

- API キーをアプリのソース・クライアントに埋め込まない。API 呼び出しはサーバー側で行う。
- `.env` やシークレット管理を使い、`.env` を Git にコミットしない。
- 画像の形式・サイズ・画素数を検証する。不要な EXIF を削除する。ユーザー画像を必要以上に保存しない。
- 外部 URL を取得する処理では SSRF 対策を行う。
- API の利用者認証、レート制限、入力検証を行う。
- エラーログに API キー・個人情報・画像データを出さない。
- 利用料金の急増を検知できるようにする。
- プライバシーポリシーに、画像の送信先・利用目的・保存期間を明記できる設計にする。

## 8. 実装前に確認・報告すること

1. 現在のフロントエンド・バックエンドの構成
2. 現在実装されている機能
3. 追加が必要な API と環境変数
4. 必要なデータベース変更
5. API の公式ドキュメントと現在の料金
6. 利用規約・商用利用条件で注意すべき点
7. 実装手順と予想される費用

API キーが未設定でもアプリ全体がクラッシュしないようにし、未設定の API を明確に表示する。**実際の API を呼び出さずに成功したように見せるダミー実装は禁止。**

## 9. 完了時の報告

- 採用した API とその用途、使用したモデル名と検索機能
- 必要な API キーと設定方法
- 商品特定の処理フロー
- 実装済み・未実装の機能
- テスト結果
- 商品特定精度を測る評価方法
- 商品 1 件あたりの実測または推定原価と、その計算根拠
- 現在の料金・規約について確認できていない点
- 次に実施すべき作業

## 最重要方針

商品特定の精度を優先しながら、API 原価を計測・管理する。実在商品を確認する根拠なしに、AI の推測だけでブランドや商品名を断定しない。API の仕様・料金・機能を捏造しない。
